# 🌐 Update Sources, Repository Linking & Signature Protection in ApkUp

This guide explains how ApkUp's update sources work together, how Source Priority & Per-App Pinning choose the best download, how Pre-Release Channels and Signature Verification protect your device, and how to link custom GitHub, GitLab, or Codeberg/Forgejo repositories.

1.2 Direct In-App Downloads from APKMirror

When Direct APKMirror Downloads is enabled under Setup ➔ APKMirror, ApkUp resolves the download link in the background, downloads the APK or .apkm bundle directly inside the app, and installs it without forcing you through ad-heavy browser pages.

  • If Cloudflare triggers an interactive check, ApkUp opens a compact in-app WebView first and only falls back to your system browser if needed.

1.3 What is an "App Signature" and why does it matter?

Every Android app carries an invisible cryptographic seal from its developer — its digital signature.

  • Android only allows an update if the new APK has the exact same signature as the installed app.
  • How ApkUp protects you: ApkUp checks signatures during update discovery and again before installation (minSdk, ABI, and signing certificate), blocking tampered or mismatched updates before Android fails on them.

1.4 Multi-Source Priority & Per-App Pinning

When an app offers updates on multiple sources simultaneously, ApkUp keeps your Updates list clean by showing each app once:

  • Global Source Priority: Open Setup ➔ Source Priority and reorder sources via drag-and-drop or arrow buttons to choose your preferred default order.
  • Per-App Source Pinning: In Apps or Updates, pin an individual app to a specific source (e.g., always prefer GitHub over Play Store). If the pinned source currently has no update, ApkUp automatically falls back to your global order.
  • Alternative Sources: Tap any update card to view all other sources offering that update and switch with one tap.

2.1 Parallel Multi-Source Aggregation & Version Verification

ApkUp queries all enabled sources concurrently and in isolation, so one slow or unreachable provider never blocks the others:

    Orchestrator --> Play["Google Play Store\n(Anonymous gplayapi)"]
    Orchestrator --> AM["APKMirror\n(REST v2 Batch API)"]

  1. Strictly higher Android versionCode (when provided by the source) and semantic version progression.
  2. Pre-install compatibility check verifying device minSdk, supported CPU ABIs, and signing certificates before launching installation.

2.2 Cryptographic Signature Verification (SHA-1 & SHA-256) & Origin Detection

ApkUp computes both SHA-1 and SHA-256 signing fingerprints via PackageManager (GET_SIGNING_CERTIFICATES on API 28+):

  • APKMirror: Strictly matches the remote SHA-1 fingerprint against the installed app.
  • F-Droid / IzzyOnDroid: Matches the local certificate against the signer SHA-256 hash recorded in the repository index.
  • Install Origin Detection: Uses PackageManager.getInstallSourceInfo() to flag cross-source signature mismatches proactively.
  • Local Export Exception: When using Save APK, file/archive/SHA-256 integrity is verified without blocking export if the installed app uses a different signer.

2.3 Direct APKMirror Resolution & Hardened .apkm Split Extraction

  1. Three-Stage Link Resolution: Variant page ➔ time-signed download page ➔ final CDN stream.
  2. Cooldown & Anti-Bot Handling: Enforces per-app 10-minute cooldowns on failures, opens an in-app Cloudflare WebView when interactive verification is needed, and falls back to the system browser if still blocked.

2.4 Google Play Store Engine (gplayapi 4.0.0) & HTTP 429 Recovery

Starting with v1.46.0+, anonymous Play Store queries run directly on-device via gplayapi 4.0.0 (PlayClient and DefaultPlaySessions) without relying on an external Aurora Dispenser server:

  • Stronger Privacy & Data Minimization: Because no third-party dispenser server sits in the middle, no external intermediary ever sees your IP address or update-check timestamps. Traffic flows directly between your device and Google Play while keeping the privacy-friendly Pixel 7a baseline profile and requiring no Google account.
  • Higher Reliability & HTTP 429 Recovery: Eliminates external dispenser outages and bottlenecks. On HTTP 429, ApkUp rotates the anonymous session in a synchronized manner with cooldown protection so concurrent checks and downloads share the refreshed session cleanly.

Part 3: Frequently Asked Questions (FAQ)

3.1 Why does ApkUp show a warning icon for a "Signature Conflict"?

Apps compiled by F-Droid use F-Droid's signing key, whereas GitHub or Play Store builds use the developer's or Google's key. Android forbids overwriting an app across different signing keys. Pick the matching source under Alternative Sources, or uninstall the existing app first if you want to switch signers.

3.2 Do I need a Google account for Play Store updates?

No. ApkUp uses anonymous guest sessions and never asks for your personal Google credentials.

3.3 Why does APKMirror sometimes open an in-app WebView or my browser?

APKMirror uses Cloudflare bot protection. When Cloudflare requires human verification, ApkUp opens an in-app WebView first (or falls back to your browser if running in the background) so you can still complete the download.

3.4 What are .apkm files and can ApkUp install them directly?

Yes! .apkm files are split APK bundles (base app + language/ABI/density splits). ApkUp extracts and installs all matching splits automatically.

3.5 How do I manage Alpha / Beta pre-releases (for apps and ApkUp itself)?
  • For Tracked Apps: Open Setup ➔ Include Pre-Releases to enable individual channels (Beta, RC, Alpha, Nightly) globally, or override pre-release behavior per app inside its details sheet. By default, pre-releases are disabled.
  • For ApkUp Itself (Self-Updater): Open Setup ➔ About ➔ Receive beta updates (disabled by default) to opt into ApkUp pre-release builds. Turning it off automatically returns you to the stable track with the next regular release.
3.6 Does ApkUp support self-hosted GitLab and Forgejo servers?

Yes! Both self-hosted GitLab (including nested subgroups) and self-hosted Forgejo instances over https:// are supported when linking repositories.

Starting with v1.40.0+, ApkUp upgrades its F-Droid and community repository processing to the modern F-Droid Index V2 specification (index-v2.json). This brings dramatic improvements in network efficiency, memory usage, and update accuracy.

1. What is F-Droid Index V2?

The F-Droid Index V2 format is the next-generation metadata catalog for Android open-source repositories. Instead of relying on monolithic, memory-intensive XML archives, Index V2 distributes repository manifests formatted as streamlined JSON objects (index-v2.json), partitioned by application packages and cryptographic release signatures.

2. Why the Upgrade from Index V1 (index.xml)?

Prior to v1.40, repository metadata was parsed from legacy index.jar / index.xml feeds. This came with significant disadvantages on mobile devices:

  • ⚠️ High RAM & CPU Consumption: Parsing a 30+ MB uncompressed XML file required tens of megabytes of heap allocation and could cause stutter on mid-range devices.
  • ⚠️ Slow Cold Checks: Reading XML tags sequentially slowed down background checks.
  • ⚠️ Bandwidth Waste: Entire catalogues had to be parsed even if only a few packages changed.

The Index V2 Advantages in ApkUp:

  • ⚡ Streaming JSON Parser: ApkUp streams index-v2.json directly from the network without allocating huge string buffers into RAM.
  • ⚡ Incremental Index-V2 Diffs & Caching: Uses ETag, Last-Modified, and signed F-Droid Index-V2 diffs (RFC 7396 JSON Merge Patch with mandatory SHA-256 verification) to download only lightweight incremental changes when your local cache is up to date, automatically falling back to the full index-v2.json when needed.
  • ⚡ Instant Package Matching: Direct hashmap lookup matching your device's installed package names in milliseconds.

3. Supported Community Repositories

ApkUp connects natively with major verified repositories inside a single unified repository manager:

  1. IzzyOnDroid (apt.izzysoft.de): The premier curated repository for open-source applications built directly from developer repositories with original developer signatures.
  2. Official F-Droid Repository (f-droid.org): The global repository for free and open-source software built from source on F-Droid build servers.
  3. Built-in Verified Presets: Ready-to-enable profiles for NewPipe Repo (archive.newpipe.net), microG Repo (microg.org), and Guardian Project (guardianproject.info) with pre-pinned SHA-256 signing fingerprints.
  4. Custom Third-Party HTTPS Repositories: Any repository implementing the F-Droid Index V2 (entry.jar / index-v2.json) or Index V1 (index-v1.jar) standard.

4. Managing Built-in & Custom F-Droid Repositories (v1.43.1+)

Starting with v1.43.1, all built-in and custom F-Droid repositories are managed in one unified bottom sheet in the Setup tab (alongside automatic detection during Obtainium imports):

  1. In ApkUp, navigate to Setup ➔ Update Sources ➔ F-Droid / IzzyOnDroid.
  2. Toggle the source on and tap the row to open the unified F-Droid Repositories bottom sheet (FDroidReposBottomSheet).
  3. Toggle any of the Built-in Repositories (IzzyOnDroid, Official F-Droid, microG Repo, Guardian Project, or NewPipe Repo) or add your own custom HTTPS repository:
  • Display Name: Label shown inside ApkUp
  • Repository URL: https://... endpoint (supports /repo, /archive, /fdroid/archive, or fdroidrepo:// links with ?fingerprint=…)
  • SHA-256 Fingerprint (Optional): 64-character hex signing fingerprint of the repository index certificate
  1. Tap Add Repository. ApkUp validates the https:// host and includes the repository in your next update scan.

5. Security, Signing Keys & Fingerprint Verification

Cryptographic JAR Verification & Optional TOFU Pinning

When fetching entry.jar (Index V2) or index-v1.jar (Index V1 fallback), ApkUp cryptographically verifies the JAR signature (META-INF/*) and enforces anti-rollback timestamp checks:

  • Explicitly Pinned Repositories: Built-in presets and custom repositories with a 64-character SHA-256 fingerprint strictly enforce that exact X.509 signing certificate (fail-closed).
  • Trust-on-First-Use (TOFU) Pinning: If you add a custom HTTPS repository without specifying a SHA-256 fingerprint, ApkUp verifies the signed entry.jar / index-v1.jar on the first successful sync, automatically pins its X.509 certificate fingerprint for all future checks, and displays a TOFU-Pinned badge in the repository sheet.

Package Signature Isolation

F-Droid builds packages with its own official signing keys, while developers signing their own releases (or packages from IzzyOnDroid / GitHub) use developer private keys. ApkUp enforces cryptographic signature matching before recommending or installing any update to ensure that Android does not reject the package with an INSTALL_FAILED_UPDATE_INCOMPATIBLE error.

By default, ApkUp accesses public developer repositories on GitHub, GitLab, and Codeberg / Forgejo anonymously. However, for active users, private repositories, or hosts with strict rate limits, adding your own Personal Access Token (PAT) provides maximum reliability.

1. Why Do I Need an Access Token?

GitHub Rate Limits: 60 vs. 5,000 Requests/Hour

GitHub strictly restricts anonymous API requests to 60 requests per hour per public IP address.

  • If you track 15–20 apps hosted on GitHub, checking for updates twice quickly exhausts this quota.
  • If you use a VPN or public Wi-Fi, other users sharing that IP also consume your quota, leading to immediate HTTP 403 API rate limit exceeded errors.
  • Adding a free GitHub Personal Access Token raises your limit immediately to 5,000 requests per hour and enables batched GitHub GraphQL queries (checking up to 20 repositories in a single API call instead of one REST request per app).

GitLab: Private Repositories & Subgroups

While public GitLab projects can often be browsed anonymously, many developers and organizations host repositories under multi-level subgroups or private team workspaces. A GitLab token ensures ApkUp can query release tags and asset URLs reliably.

7. Privacy & Security FAQ

Where are my tokens stored?

Your tokens are stored exclusively on your device in Android's private, sandbox-isolated application storage encrypted at rest via Google Tink (AES-256-GCM) backed by the Android Keystore (SecurePrefsStore), with cloud backup disabled (allowBackup="false").

Does ApkUp transmit my tokens to any third-party server?

Never. ApkUp enforces strict host isolation: your GitHub token is sent exclusively to api.github.com, your GitLab token exclusively to gitlab.com, and your Codeberg token exclusively to codeberg.org / *.codeberg.org over HTTPS (tokens are stripped automatically on cross-host redirects and are never sent to third-party custom domains). There are no intermediate telemetry, analytics, or proxy servers.

Can a token be revoked?

Yes, at any time. Simply visit your GitHub, GitLab, or Codeberg token management settings and click Revoke or Delete.

<a name="23-packagemanager-shell-pipeline--play-store-attribution-comandroidvending"></a>

2.3 PackageManager Shell Pipeline & Play Store Attribution (com.android.vending)

When installing via Shizuku, ApkUp executes a multi-stage transaction against the Android system package manager (pm):

  1. Isolated Staging & GZIP Verification:

All downloaded package artifacts (single APK, extracted .apkm splits, or compressed Google Play splits) are staged in the private app cache and automatically decompressed if a GZIP magic header (0x1f8b) is detected.

  1. Session Creation with Play Store Origin:

```bash

pm install-create -r -i com.android.vending

```

  • -r: Replaces the existing application while preserving all user data (INSTALL_REPLACE_EXISTING).
  • -i com.android.vending: Sets the official installation origin (installerPackageName) to the Google Play Store. This ensures full compatibility with apps that verify at runtime whether they were installed from an official store source.
  1. Streaming Package Data via Standard Input (stdin):

For each APK split file, binary data is piped directly through a file descriptor stream into the pm process:

```bash

pm install-write -S <byte_size> <session_id> <split_name.apk> -

```

Piping directly over stdin cleanly avoids SELinux file access restrictions on private application directories.

  1. Atomic Commit & Rollback Protection:

```bash

pm install-commit <session_id>

```

<a name="31-do-i-need-root-access-on-my-phone-to-use-shizuku"></a>

3.1 Do I need Root access on my phone to use Shizuku?

No! Starting with Android 11, Shizuku works completely without Root using Android's built-in Wireless Debugging feature. However, if your device is rooted (e.g., via Magisk, KernelSU, or APatch), Shizuku can optionally be started directly via Root — which is even faster and requires no pairing code.

<a name="32-will-shizuku-void-my-warranty-or-break-banking-apps"></a>

3.2 Will Shizuku void my warranty or break banking apps?

No, your warranty remains 100% intact and all banking apps continue to work normally. Because Shizuku neither unlocks the bootloader nor modifies system partitions (Root), Google's security checks (Play Integrity / SafetyNet) and Samsung Knox remain completely untouched.

<a name="33-why-do-i-have-to-restart-shizuku-after-rebooting-my-phone"></a>

3.3 Why do I have to restart Shizuku after rebooting my phone?

If your phone is not rooted, Android terminates all debugging services whenever the device is completely powered off or restarted for security reasons.

  • You do not have to repeat the 6-digit pairing process!
  • After rebooting your phone, simply open the Shizuku app and tap "Start" once (takes about 3 seconds).

<a name="34-issue-wireless-debugging-is-grayed-out-and-cannot-be-turned-on"></a>

3.4 Issue: "Wireless debugging" is grayed out and cannot be turned on!

Cause: Android only allows enabling Wireless debugging while your smartphone is connected to a Wi-Fi network.

  • Solution: Connect your phone briefly to your home Wi-Fi (or a mobile hotspot) and start Shizuku. As soon as Shizuku says "Shizuku is running", you can turn Wi-Fi off again — the service will stay active!

<a name="35-issue-shizuku-searches-endlessly-for-the-pairing-service-or-the-code-input-never-appears"></a>

3.5 Issue: Shizuku searches endlessly for the pairing service or the code input never appears!

This behavior occurs most frequently on smartphones from Xiaomi (MIUI / HyperOS), Oppo/Realme, and Samsung:

  1. Notification Style (Xiaomi): Go to Android Settings ➔ Notifications & Control center ➔ Notification shade and switch it from "MIUI" to "Android" (Classic). Otherwise, the text box for entering the pairing code inside the notification cannot be expanded.
  2. USB Debugging (Security settings): On Xiaomi devices, open Developer options and enable "USB debugging (Security settings)" in addition to standard USB debugging.
  3. Notification Permission: Make sure you have granted the Shizuku app permission to display notifications.

<a name="36-issue-shizuku-stops-by-itself-in-the-background-after-a-while-xiaomi-samsung-oneplus"></a>

3.6 Issue: Shizuku stops by itself in the background after a while (Xiaomi, Samsung, OnePlus)!

If Shizuku stops after a few hours on its own, this is caused by aggressive OEM battery-saving policies or Android 12/13's Phantom Process Killer:

  • Solution 1 (Battery Optimization): Long-press the Shizuku app icon ➔ App info ➔ Battery and select "Unrestricted".
  • Solution 2 (Developer Options on Android 13+): In Developer options, enable the toggle "Disable child process restrictions".
  • You can also find manufacturer-specific instructions on DontKillMyApp.com.

<a name="37-what-happens-if-shizuku-stops-while-apkup-is-downloading-an-update"></a>

3.7 What happens if Shizuku stops while ApkUp is downloading an update?

ApkUp will not crash and your downloaded update will not be lost! If ApkUp detects that the Shizuku service is unresponsive at the moment of installation, the app automatically and seamlessly falls back to the standard Android package installer and shows the regular Android confirmation prompt.

<a name="38-does-update-all-also-work-without-shizuku"></a>

3.8 Does "Update All" also work without Shizuku?

Yes, of course. Even without Shizuku, tapping "Update All" downloads all updates in the background. The only difference is that without Shizuku, you briefly tap "Update" in the Android system dialog for each downloaded app.

<a name="39-why-does-my-phone-recognize-apps-installed-via-shizuku-as-installed-from-google-play-store"></a>

3.9 Why does my phone recognize apps installed via Shizuku as "Installed from Google Play Store"?

This is an intentional feature of ApkUp! When ApkUp installs an app via Shizuku, it passes the parameter -i com.android.vending (the official package identifier of the Google Play Store) to Android. Some apps otherwise refuse to run or display warnings if they detect they were updated outside the Play Store. Thanks to this attribution, all updated apps behave as if they came directly from the official store.

3.10 How does the optional Root Installer (su) work alongside Shizuku?

Starting with v1.43.0+, rooted devices (Magisk, KernelSU, or APatch) can optionally enable Root Installer (su) under Setup ➔ Installation & Automation:

  • Smart Fallback or Standalone: When both Shizuku and Root are enabled, ApkUp uses Shizuku first and seamlessly falls back to su if Shizuku was not restarted after a reboot. If Shizuku is disabled, ApkUp uses su directly for silent foreground and autonomous background updates (while excluding uninstalled Watchlist apps from unattended background installs).
  • Pre-Install Integrity Verification & Origin Preservation: Before opening a pm install-create session, RootInstaller verifies all staged base and split APKs via ApkIntegrityVerifier (fail-closed) and preserves the existing installer package origin (-i).
  • Interactive Root Check Bottom Sheet: Tapping the Root Installer (su) row opens the dedicated RootSetupBottomSheet where you can verify superuser availability live at any time. For security, importing a configuration backup resets useRootInstaller to false until you re-enable it on the device.
  • Completely Optional: On non-rooted phones, keep this option turned off and continue using Shizuku or the normal Android installer.

When checking for updates or downloading packages, ApkUp communicates with multiple independent providers (Google Play Store, APKMirror, F-Droid / IzzyOnDroid, GitHub, GitLab, and Codeberg / Forgejo). If a source check or installation fails, ApkUp links directly to the matching section below.

1. Understanding the Error Types

  1. Network & Source Check Failures: The remote server was unreachable, rate-limited the request, or returned an HTTP error.
  2. Package & Installation Failures: The download completed, but Android's PackageManager, ApkUp's pre-install compatibility check (minSdk / ABI), or cryptographic signature verification rejected the package.

2. Network & Connectivity (DNS & Timeout)

DNS Resolution Failed (UnknownHostException)

  • Symptom: UnknownHostException, dns lookup failed, or Unable to resolve host.
  • Cause: Your device could not resolve the server hostname (e.g., api.github.com, gitlab.com, codeberg.org, or apt.izzysoft.de). Common culprits are Private DNS (DoH/DoT), VPN ad-blockers (AdGuard, NextDNS, Pi-hole), or switching networks.
  • Solution:
  1. Confirm general internet connectivity in your browser.
  2. Temporarily set Android Settings ➔ Network & Internet ➔ Private DNS to Automatic.
  3. Allowlist repository domains in any ad-blocking VPN (github.com, gitlab.com, codeberg.org, apkmirror.com, apt.izzysoft.de, f-droid.org).

Connection Timeout (SocketTimeoutException)

  • Symptom: SocketTimeoutException or Read timed out.
  • Cause: The remote server took too long to respond (peak traffic or high-latency mobile connection).
  • Solution:
  1. Pull down on the Updates tab to retry.
  2. If one specific source times out repeatedly, open Setup ➔ Source Health & Cooldowns to inspect cooldowns, or temporarily toggle that source off in Setup.

3. Authentication & Rate Limits (HTTP 401, 403, 429)

GitHub Rate Limit Exceeded (HTTP 403)

  • Symptom: HTTP 403: API rate limit exceeded.
  • Cause: GitHub limits unauthenticated requests to 60 requests per hour per IP. Tracking many GitHub apps or sharing a VPN/public Wi-Fi IP exhausts this quickly.
  • Solution:
  • Add a free GitHub Personal Access Token (raises the limit to 5,000 requests/hour and enables batched GraphQL queries).
  • Follow the Token Setup Guide, then paste it under Setup ➔ GitHub ➔ Test Token.

Google Play Store Rate Limit (HTTP 429)

  • Symptom: HTTP 429: Too Many Requests or Play Store download failure.
  • Cause: Anonymous Play Store guest sessions (gplayapi 4.0.0) are temporarily rate-limited by Google, or the app is a paid/region-locked app requiring a personal license.
  • Solution:
  1. Wait 5–10 minutes — ApkUp automatically rotates anonymous sessions with synchronized cooldown protection.
  2. Open the update card and switch to APKMirror, F-Droid, or GitHub/GitLab under Alternative Sources if available.

GitLab / Codeberg Authentication Error (HTTP 401 / 403)

  • Symptom: HTTP 401 Unauthorized or HTTP 403 Forbidden.
  • Cause: The linked project is private, belongs to an internal group, or your stored Personal Access Token expired/lacks scope (read_api for GitLab, read:repository for Codeberg/Forgejo).
  • Solution:
  • Open Setup ➔ GitLab (or Codeberg), update your token, and tap Test Token.

4. Server & Availability Errors (HTTP 404, 5xx)

APKMirror 404 Not Found

  • Symptom: ApkUp detects a new APKMirror version, but downloading fails with HTTP 404.
  • Cause: APKMirror's RSS/API feed occasionally publishes a release before all architecture variants finish propagating across CDN nodes.
  • Solution:
  • Wait 15–30 minutes and retry.
  • Tap the app card and choose Open in Browser to inspect the variant page directly.

Upstream Server Errors (HTTP 500, 502, 503, 504)

  • Symptom: 502 Bad Gateway, 503 Service Unavailable, or 504 Gateway Timeout.
  • Cause: Temporary outage or maintenance at the upstream provider.
  • Solution: No action needed — ApkUp's Source Health tracker handles temporary outages automatically and retries on your next check.

5. APKMirror Cloudflare Challenges & Browser Fallback

  • Symptom: APKMirror prompts for verification or opens your browser.
  • Cause: Cloudflare bot protection flagged automated traffic or your VPN/proxy IP.
  • Solution:
  1. When Cloudflare triggers a challenge during a foreground download, ApkUp opens an in-app WebView so you can complete the check without leaving the app.
  2. If it runs in the background or still fails, ApkUp automatically opens your device browser as a seamless fallback and enforces a 10-minute per-app cooldown to prevent repeated blocks.

6. Installation & Signature Conflicts (INSTALL_FAILED_UPDATE_INCOMPATIBLE)

  • Symptom: Android rejects installation with INSTALL_FAILED_UPDATE_INCOMPATIBLE, or ApkUp flags a Signature Mismatch warning.
  • Cause: Every Android app update must be signed with the exact same private cryptographic key as the installed app. Cross-updating between different signers (e.g., Google Play vs. F-Droid build servers vs. developer GitHub release) is blocked by Android and ApkUp's pre-install verifier.
  • How to Resolve:
  1. Open the update card and pick a matching source under Alternative Sources (or pin the app to its original source).
  2. If you intentionally want to switch signers (e.g., Play Store ➔ GitHub), uninstall the existing app first (back up its data beforehand!) and install the new build cleanly.
  3. Exporting APKs (Save APK): Saving an .apk locally still works even if the installed app uses a different signature — ApkUp verifies file/archive/SHA-256 integrity without blocking local export.

7. Custom Repository Linking & Asset Matching

  • Symptom: "No matching release asset found" or repository lookup error.
  • Cause: The release only contains source archives (.zip / .tar.gz), desktop binaries, an incompatible CPU architecture (ABI) / minSdk, or a custom asset filename that doesn't match your filter.
  • Solution:
  1. Verify on the repository's Releases page that a compiled Android .apk exists.
  2. Check your repository slug format in Apps ➔ Link Repository:
  • GitHub: owner/repository
  • GitLab: group/project or nested group/subgroup/project
  • Codeberg / Forgejo: owner/repository (plus custom host if self-hosted)
  1. If the release ships multiple APK variants (e.g., FOSS vs. Play or architecture splits), add an optional APK Asset Regex and test it live in the repository sheet.

8. F-Droid / IzzyOnDroid & Codeberg / Forgejo Issues

  • F-Droid / IzzyOnDroid: If a custom repository fails certificate verification (TOFU or fingerprint mismatch), open Setup ➔ F-Droid / IzzyOnDroid, verify the HTTPS URL and 64-character SHA-256 fingerprint, and see the F-Droid & Index V2 Guide.
  • Codeberg / Forgejo: Self-hosted Forgejo instances must use https:// and expose the standard /api/v1/repos/.../releases endpoint. See Token Configuration for private repos.

9. Quick Diagnostic Checklist

  1. Pull to Refresh on the Updates tab.
  2. Check Setup ➔ Source Health & Cooldowns to see if a source is temporarily cooled down.
  3. Temporarily test without VPN / Private DNS if DNS or Cloudflare errors persist.
  4. Add a free GitHub / GitLab / Codeberg Token for heavy repo lists.
  5. Need help? Export a sanitized report via Setup ➔ Diagnostics ➔ Export / Share and attach it to a GitHub Issue.

Every APK you download from GitHub Releases or a mirror can be verified in seconds before you install it. This guide explains what SHA-256 and APK signing certificates are, why they protect you, and how to check them step by step.

What is a SHA-256 Checksum?

A SHA-256 checksum (also called a hash or digest) is a unique 64-character digital fingerprint calculated from the exact bytes of an APK file.

  • Tamper detection: Changing even a single bit inside an APK produces a completely different 64-character hash.
  • Download integrity: If a download is corrupted, incomplete, or modified by a third-party mirror, the SHA-256 hash will not match the official SHA256SUMS published by ApkUp's GitHub Actions release pipeline.
  • Single-Artifact Principle: All official ApkUp releases are built and signed once by GitHub Actions (release.yml), so the SHA-256 hash is identical everywhere.

Local Verification (Step-by-Step)

You can verify the downloaded .apk file on your PC or Mac in 10 seconds before transferring or installing it:

Windows (PowerShell)

  1. Open PowerShell in your Downloads folder (or cd $HOME\Downloads).
  2. Run:
Get-FileHash .\ApkUp-*.apk -Algorithm SHA256
  1. Compare the printed Hash (case-insensitive) with the Live SHA-256 Checksum shown on ApkUp Downloads or in SHA256SUMS on GitHub Releases.

Linux

  1. Download both the .apk and SHA256SUMS from GitHub Releases into the same folder.
  2. Run:
sha256sum -c SHA256SUMS
  1. Look for ApkUp-v....apk: OK.

macOS

  1. Open Terminal in your Downloads folder (cd ~/Downloads).
  2. Run:
shasum -a 256 ApkUp-*.apk
  1. Compare the output hash with the official hash on ApkUp Downloads.

Automatic Protection Inside ApkUp (APK Signature v2/v3)

You do not have to run manual checks when updating apps inside ApkUp:

  • Signing Certificate Pinning: Before installing any app update, ApkUp cryptographically verifies the APK's v2/v3 signing certificate against the currently installed app. Even if a mirror served a modified APK, Android and ApkUp reject it.
  • SHA-256 & F-Droid Index Verification: ApkUp validates SHA-256 digests and signed F-Droid Index V2 metadata automatically during downloads.
  • Downgrade & ABI Guards: Version downgrades and incompatible ABIs/minSdk builds are blocked before installation.

Starting with Google's regional enforcement on September 30, 2026 (including Brazil, Indonesia, Singapore, and Thailand) and its global rollout in January 2027, certified Android devices introduce mandatory developer identity verification via Google Play Protect. This page explains what changes for everyday users, how to permanently unlock independent apps in Developer Options, and why ApkUp supports Keep Android Open.

1. What Changed — And When?

Under Google's Android Developer Verification policy (enforced via Google Play Services and Google Play Protect):

  • September 30, 2026 (Pilot Regions): Google Play Protect began blocking APKs from unregistered developers by default in pilot markets.
  • January 2027 (Global Rollout): Enforcement expands worldwide to certified Android devices — even for apps never distributed through Google Play.
  • Mandatory ID & Key Binding: Developers are required to submit government-issued ID, pay a registration fee, and link their package IDs and signing keys to a Google identity.

2. Step-by-Step: Unlock "Apps from Unverified Developers" (24h Flow)

If Play Protect blocks an independent APK with an "Unverified developer" notice, Google places the override inside Developer Options behind a one-time 24-hour cooldown:

  1. Enable Developer Options:
  • Open Settings → About Phone (on Samsung: Software information).
  • Scroll to Build Number and tap it 7 times until "You are now a developer!" appears.
  1. Open the Unverified Developers Setting:
  • Go to Settings → System → Developer Options (or search for Developer Options in Settings).
  • Tap Apps from unverified developers → Allow apps from unverified developers.
  1. Confirm Lock Screen & Restart:
  • Enter your PIN/password/biometrics and restart your phone when prompted.
  1. Wait the 24-Hour Cooldown:
  • Android starts a mandatory 24-hour waiting period after reboot.
  1. Choose "Allow Indefinitely" (Avoid the 7-Day Trap!):
  • After 24 hours, return to Developer Options → Apps from unverified developers.
  • Select Allow indefinitely (do not pick the 7-day temporary window, or Android will turn the setting back off after 7 days and force another 24-hour wait!).

3. What This Means for You & Open Escape Hatches

Without unlocking Developer Options, tapping direct APKs from GitHub, GitLab, Codeberg, or independent sites can be blocked by Play Protect. Once you choose Allow indefinitely — or install via Android's developer pipeline — ApkUp continues working seamlessly:

  • Direct ADB from PC (no 24h wait): adb install -r ApkUp.apk
  • Shizuku (Android 11+, no root): Uses Wireless Debugging & elevated PackageInstaller sessions inside ApkUp.
  • Root (su): Installs updates directly via Magisk, KernelSU, or APatch.
